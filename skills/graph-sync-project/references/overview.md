# Graph Sync Overview

## Purpose

- Provide stable context for coding agents working on `worai graph sync`.
- Prevent configuration and behavior drift from SDK runtime semantics.

## What A Graph-Sync Project Does

WordLift hosts one knowledge graph per account. Its entities are schema.org types in JSON-LD. A graph-sync project reads the client's pages, extracts data with XPath, turns it into schema.org entities through YARRRML mappings, and writes them into the account's graph. The client's site then shows, for each page URL, the entities WordLift serves for it (the API link). Entities reference each other, and those links are the graph: an entity that nothing references, and that references nothing, is not allowed.

## Project Contract

- Primary workflow: run the project's graph-sync command for one profile (`references/local-runs.md`). Resolve the CLI with `references/cli-resolution.md`; do not assume a global `worai`.
- Profile config section: `[profiles.<name>]` in `worai.toml`; shared settings in `[profiles._base]` (`references/config.md`).
- Each profile names the account it writes to with `api_key` (normally `${WORDLIFT_API_KEY}` from `.env`).
- Ingestion is explicit: `ingest_source` (`sitemap`, `sheets` or `urls`) and `ingest_loader` (`crawler` by default), plus `ingest_timeout_ms = 600000` with the crawler (`references/crawler.md`).
- `wordlift-sdk` is the source of truth for supported `worai.toml` keys. The project's `uv.lock` decides the local SDK version; check it before assuming config semantics. `worai` is the command runner around the SDK.
- The generated GitHub workflow runs `uv sync --locked --no-dev`, then `wordlift/graph-sync@v6`, which installs its own `worai` and SDK into system Python. The project's lock applies only to the postprocessor worker subprocesses (`references/local-runs.md`, "Why A Green Local Run Doesn't Prove CI").
- Generated repositories start with `# Generated by graph-sync-template vX` in `pyproject.toml`.

## Processing Order

Per run:

1. Load the profile; resolve every profile's `${VAR}` values.
2. Read the source URLs (sitemap, sheet tab or list) and filter them with `url_regex` / `sitemap_url_pattern`.
3. Write the static templates once, before the first page, in one bulk write.

Per URL:

1. Fetch the page with the loader. The fetched page's final URL becomes `__URL__`.
2. Convert the HTML to XHTML (the SDK's `HtmlConverter`).
3. Resolve the mapping from the routes (first match, then the fallback) and render its template (`.j2` / `.liquid`).
4. Materialize the mapping with `worph`. A mapping that produces no nodes fails the URL.
5. Run the postprocessor chain: the built-in root ID reconciler, then the custom postprocessors in manifest order, then the built-in canonical IDs, then the built-in import annotation.
6. Validate with SHACL (`warn` by default).
7. Compute the import hash; when it equals the stored one, skip the write.
8. With `--debug`, write the page graph to `output/debug_cloud/<profile>/`.
9. Write to WordLift (`put` or `patch`, `references/config.md`).

A failure on one URL doesn't stop the others; the run ends with `Total URLs: N, Successes: N, Failures: N`.

What a sync never does:

- **Delete.** A page removed from the source, a changed title, a changed type or a dropped template entity leaves its old entities in the graph (`references/kg-checks.md`).
- **Skip work by date.** It processes every source URL each run; unchanged pages cost a fetch but no write (import hash).

## Repository Layout

```text
worai.toml
.env                              # API key, Sheets service-account path (git-ignored)
pyproject.toml, uv.lock           # Python 3.12, wordlift-sdk, worai in the dev group
profiles/_base/
  exports.toml.j2                 # shared IRIs and constants
  mappings/<type>.yarrrml.j2      # shared mappings
  templates/20_organization.ttl.j2, 20_website.ttl.j2, ...
  postprocessors.toml             # custom postprocessors (a profile file replaces it)
profiles/<profile>/               # profile-specific overrides, often empty
src/<package>/postprocessors/     # custom postprocessor classes
tests/
.github/workflows/graph-sync.yml
output/                           # reports, debug graphs, fetched pages (git-ignored)
```

The package name comes from the project name (`graph-sync-example-com` → `graph_sync_example_com`); older repositories name it after the domain. Check `src/` before writing class paths.
